# Nimlo security

Nimlo shares a PC workspace with paired browsers. The PC host controls whether paired devices can edit files in the editor, use the terminal, and use AI. Enabled terminal and AI tools use the host OS user's permissions; editor path checks and permission toggles are not an OS sandbox. Pair only devices you own and trust.

This review fixes specific security defects and tests the implemented boundaries. It does not establish “100% secure,” full OWASP ASVS compliance, or protection against a compromised PC, browser, trusted device, provider CLI, or tunnel operator.

## Device access

Only the authenticated PC host can change session-wide access, individual device permissions, AI settings, internet access, project attachments, or issue invitations. Paired devices can choose and read existing attached projects and sign out their own credential. Session-wide editor/terminal/AI limits intersect with each paired credential's permissions; denying a permission in either place denies it for every tab using that credential. Current permissions are checked on commands and protected output, including existing connections. Starting AI and affirmative tool approvals require all three permissions. A terminal-enabled device can change files through its shell even with editor editing disabled.

Session-wide access settings persist; per-device overrides last for that paired credential. An absent settings record keeps existing full-access defaults. Malformed, oversized, insecure or unsupported records fail closed with device access disabled until the PC host saves safe settings. Turning off **Allow connected devices** invalidates paired credentials and pending invitations and blocks new pairing. The PC host keeps full access, acknowledged buffers and running terminal/AI work; changing access does not stop processes or undo completed actions.

## Pairing

Use **Session → Pair a device → Create internet link** on the PC. Choose **Copy invitation link**, transfer that complete invitation to your phone, open it, and enter the six-digit code and pairing password if one is set. The link contains a random 256-bit invitation secret in its fragment (`#invite=…`); the address without that fragment cannot pair. The browser removes the fragment from its visible history entry and submits the secret in the pairing request body. URL query parameters cannot authenticate. A signed-out page has a complete-link input so missing invitations can be recovered without weakening enrollment.

The optional password protects new device pairing in addition to the invitation and code. It must contain 8–128 Unicode characters and at most 512 UTF-8 bytes. Changing or clearing it cancels pending invitations and preserves already paired credentials. Only a salted Argon2id PHC hash is persisted, never the password; public snapshots contain only whether a password is set. The version-19 profile uses 19 MiB, two passes and one lane, with exact parameter, salt and digest validation before verification to prevent an edited record from requesting excessive work. Hashing runs on blocking workers and retains no KDF allocation. The bounded 4 KiB policy record is written atomically; Unix reads reject symlinks and nonregular files and require owned private directory/file permissions of 0700/0600.

To survive refresh before pairing, the browser keeps at most one pending invitation in origin-scoped tab session storage, with a two-minute local deadline. Refresh preserves that deadline rather than extending it. Successful sign-in, explicit invitation replacement and observed expiration remove it. The server's original expiry, single-use redemption, mandatory code and exact-origin checks remain authoritative. Browser storage is best effort; if it is unavailable, reopening or pasting the complete link remains possible. This stores an invitation capability, not the host or paired session credential, and does not make enrollment durable across host restarts.

Both the invitation and its code expire after two minutes and work once. **New invitation** replaces both, so copy the new link too. Each additional device receives a fresh PC-issued invitation into the same session. Five incorrect code or password submissions with the matching invitation invalidate that invitation. Missing, malformed, unknown, or wrong-origin invitation secrets do not spend its attempt budget. There is no shared proxy-IP lockout; untrusted forwarded IP headers are never used as identity. An observer who has the link, code and any configured password can redeem them first, so share them privately. This is capability-based device enrollment, not phishing-resistant MFA.

An invitation can be exchanged only at the exact origin selected when it was created. The resulting random 256-bit session credential stays bound to that origin. Credentials cannot cross between public internet, LAN, and localhost authorities. Origin binding restricts where a credential works; it does not bind it cryptographically to a physical device. A stolen credential can still be replayed at its authorized origin until expiration or revocation.

Internet cookies use `__Host-nimlo_session`, `Secure`, `HttpOnly`, `SameSite=Strict`, `Path=/`, and no Domain attribute. Local HTTP cookies use `nimlo_session`, HttpOnly and SameSite=Strict. Tokens are generated by the cryptographic random generator, compared with the `subtle` constant-time comparison primitive, and retained only in bounded host memory. Neither session credentials nor invitation secrets are included in shared device lists or broadcasts. Host restart discards all credentials.

The private PC launch credential is accepted only through an actual loopback connection using an allowed local HTTP authority, with no proxy-forwarding markers. Public and LAN authorities cannot exchange that credential for a session. Supported listener bindings are loopback, `0.0.0.0`, and `[::]`; a specific non-loopback address would prevent private PC login and is rejected.

The PC entry page offers **Open editor** instead of requiring a terminal-link paste. Its unauthenticated `POST /api/pc/open` can only invoke the OS default-browser opener with a generated private link at the request's verified local authority. It returns an opened/error status, never the link, credential, cookie or workspace. Admission requires an actual loopback peer, admitted local HTTP Host, exact mandatory Origin, no proxy-forwarding markers and the custom `X-Nimlo-Launch: 1` header. Supplied Fetch Metadata must describe a same-origin script request. Form/navigation requests and cross-origin preflights cannot invoke it. Openers are single flight, rate limited to one attempt per five seconds, and killed/reaped on the five-second timeout or shutdown.

An unauthenticated bootstrap exposes whether pairing requires a password; verified local requests may also return the nonsecret canonical PC origin alongside the 401 error. Fresh PC entry uses that origin to reuse launcher-origin cookies. The app preserves invitation/token origins, already-loaded sessions and pending alias drafts; recovery opens that tab's verified local authority. The root HTML never redirects invitations. Browser-opener success is not authentication: the entry page closes only after a real authenticated WebSocket opens. Same-profile recovery polls only for a bounded eight-second window after explicit opening; another browser or failed opener exposes a secondary private-link fallback. No durable credential store or authentication bypass was added; restart still rotates every host and paired credential.

## Expiration and revocation

Paired sessions expire after 30 minutes without an authenticated application command, or eight hours after their PC-issued authorization, whichever comes first. HTTP bootstrap, WebSocket pong, and application ping do not refresh that idle deadline. Keepalive traffic cannot make a stolen inactive credential last indefinitely. Paired devices cannot issue invitations; re-pair through the PC for a fresh authorization.

Click **Session** in the header to open the session's browser list. Its count measures connected browsers, including extra tabs, rather than unique physical devices. The PC host's **Revoke** signs out a device and every tab using its credential. **Sign out** ends your own paired credential. The PC host's **Sign out paired devices** invalidates all paired credentials, including credentials that have not connected a WebSocket yet, and cancels outstanding invitations. The private PC session remains available. Revocation and expiration preserve acknowledged buffers and running terminal/AI processes; they close access to those processes. Pending local drafts remain on their originating browser tab.

HTTP authentication, WebSocket admission, every application command, resynchronization, and outgoing protected data check the current credential. An authentication-change signal cancels pending WebSocket sends and closes revoked sockets with policy code 1008; a periodic expiry sweep removes idle records. Device identifiers cannot replace a connection owned by another credential. Per-device project identities and generations fence file and terminal commands; document revisions independently prevent stale writes. Each device can choose an attached project without moving other devices. Folder expansion returns bounded metadata without selecting the project. One authenticated session grants access to every attached folder; attachment does not create another public endpoint or credential. Removing a folder detaches it for all devices, refuses unsaved or running work, and leaves files on disk.

Revocation cannot undo commands already executed or bytes already delivered. An already-compromised trusted session can use its intentional shell access to read host secrets, alter files, or create persistence outside Nimlo. Run Nimlo as an ordinary OS user with only the access you need. The security boundary protects against unpaired network clients, malicious external web pages, accidental credential transport, and continued use of expired or revoked Nimlo credentials; it does not contain a malicious trusted administrator.

## Transport and browser boundaries

The native app uses a random loopback port. The standalone companion host defaults to `127.0.0.1:8875`. Internet mode works with this loopback listener: the managed connector initiates its outbound tunnel without opening a router port. Public browser traffic uses HTTPS/WSS. Cloudflare terminates TLS and forwards traffic to the PC's loopback HTTP listener; this is not encryption that hides workspace contents from the tunnel provider. AI requests likewise send selected context to the selected provider through its official CLI.

LAN access is an explicit option: `./scripts/run.sh --workspace /path/to/project --listen 0.0.0.0:8765`. LAN HTTP has no transport encryption, so a network observer or active attacker can read or tamper with code, invitations, credentials, and shell traffic. Use internet HTTPS mode or a trusted encrypted private tunnel when transport confidentiality matters. An externally managed permanent tunnel must preserve the exact configured Host, support WSS, terminate HTTPS correctly, and forward only to the loopback listener. Do not publish an unencrypted listener directly.

Nimlo checks the exact Host and Origin combination, rejects duplicate Host/Origin headers, and requires Origin on pairing and WebSocket handshakes. Proxy headers never confer PC-native privileges. Disabling or losing a managed internet link invalidates that public authority and closes its sockets. Tunnel configuration is isolated from user configuration and unsafe overrides; its process group is stopped and reaped on shutdown.

Application HTTP responses carry no-store, no-referrer, nosniff, frame denial, restrictive CSP, a same-origin resource policy, and disabled camera/microphone/geolocation permissions. Accepted HTTPS responses also carry HSTS. File names, source code and terminal text render as plain text or escaped highlighted text. Supported AI Markdown is assembled with DOM nodes and text content; it does not interpret raw HTML or load images. External links allow only HTTP(S), with a separate tab and opener isolation. Local AI file links pass through authenticated host resolution against attached roots, then the ordinary project/file commands; arbitrary host paths, symlinks, traversal and executable URL schemes cannot open files. Terminal clipboard, hyperlink, and graphics control strings are discarded. There are no remote scripts, analytics, or browser runtime dependencies. Sensitive drafts in browser session storage are accessible to that browser profile and are removed as acknowledged drafts are resolved; screen locks and browser-profile security remain your responsibility.

## Resource, filesystem, and process limits

There are at most 64 accepted TCP streams, including HTTP connections and upgraded WebSockets; excess streams are dropped without queued admission tasks. Incomplete HTTP headers have an absolute ten-second deadline and a 16 KiB read-buffer/32-header limit. Reads expire after 60 seconds without incoming data. HTTP requests have an eight-second handling deadline and pairing bodies a 4 KiB limit. There are at most eight simultaneous browser connections and 16 total credentials including the PC credential. Existing file, history, terminal, AI, and message bounds are described in README.md. These bounds limit retained resources; they cannot guarantee availability under bandwidth saturation, repeated flooding, or an OS-level attack.

On Unix, editor file access uses directory handles and no-follow opens for workspace components. Nonblocking opens and opened-handle regular-file checks prevent FIFOs from hanging document/recovery reads. Recovery reads remain bounded if a file grows after inspection; recovery lock opens reject symlinks and non-regular files. Recovery/settings directories and files use private permissions. The attached-folder registry is bounded private metadata written atomically; inactive folders acquire recovery state and file handles only when selected. A same-user process that can alter the host environment, private recovery directories, or executable search path is already inside the trusted OS boundary. Windows path races and process-tree behavior need separate validation.

Official provider CLIs run on demand. The shared, persisted AI permission mode defaults to Ask. Codex uses on-request approvals with a read-only sandbox; Claude uses manual tool approval. Explicit Full access uses Codex's danger-full-access / never policy and Claude's permission bypass. Full access deliberately gives the provider the host account's command, filesystem and network access, which can extend beyond attached roots. The browser file-link resolver and Nimlo authentication do not sandbox an authorized AI process. Native provider or administrator restrictions may still refuse a policy.

Approval previews contain the complete actionable command, folder, file changes or permission scope, rather than provider request IDs and duplicated output. Oversized or incomplete actions cannot be granted, and the UI states the reason. Codex choices follow its available decisions, with exact wire values retained on the host. Pending decisions are bounded and consumed once. Any affirmative decision is refused while that project's editor has unsaved work. Changing settings is refused while any AI job is active and resets dormant provider conversations before the next job. Starting AI still requires saved or discarded buffers in either mode; concurrent later disk changes retain the existing conflict protections.

Sign-in probes use a dedicated process group and cleanup guard, including success, timeout, and cancellation. Nimlo does not read provider credential files. Tests use fake providers and send no paid inference requests. CLI configuration, inherited environment, operating-system security, and external dependency updates remain outside the locked application test suite.

## Review evidence and maintenance

The comparison references are [OWASP ASVS 5.0.0 authentication](https://github.com/OWASP/ASVS/blob/v5.0.0/5.0/en/0x15-V6-Authentication.md), [session management](https://github.com/OWASP/ASVS/blob/v5.0.0/5.0/en/0x16-V7-Session-Management.md), [web frontend security](https://github.com/OWASP/ASVS/blob/v5.0.0/5.0/en/0x12-V3-Web-Frontend-Security.md), and the [WebSocket Security Cheat Sheet](https://cheatsheetseries.owasp.org/cheatsheets/WebSocket_Security_Cheat_Sheet.html). Reviewed control areas include authentication pathway documentation and abuse prevention (6.1.1/6.1.3, 6.3.1/6.3.4), random single-use enrollment (6.4.1), random backend-validated sessions (7.2), documented idle/absolute lifetime (7.3), session termination (7.4/7.5), cookie/header/output handling (V3), and WebSocket origin/session controls (4.4). Local HTTP transport and bearer-capability enrollment have the explicit limits above; full ASVS Level 2 certification is not claimed.

Run `cargo test --locked`, strict Clippy, `node scripts/pairing-check.cjs`, and the existing security/browser/setup/UI/resize/internet checks. `scripts/multi-project-check.cjs` additionally verifies cross-project command scope, duplicate filenames, independent device selection, recovery and shared resource bounds; `scripts/multi-project-review.cjs` exercises the combined tree in Chromium and WebKit. The dedicated pairing script tests a disposable local proxy authority, unknown-invitation abuse, origin replay, URL-token rejection, code limits, rotation, permitted paired file/terminal access, immediate multi-tab revocation, post-revocation data fencing, self logout, and re-pairing. Unit tests exercise expiration without long waits, host-only controls, live permission limits, password validation and private fail-closed persistence. `scripts/internet-live-check.cjs` separately checks actual public HTTPS/WSS with a disposable project. Development test tools are not runtime dependencies.

`cargo audit --json` checks Cargo.lock against the current RustSec database; its timestamp, advisory database revision, and results are stored in `tests/dependency-audit.json`. A clean advisory scan detects known listed dependency vulnerabilities at that time, not unknown defects or all installed host software. Repeat it and these checks when dependencies or authentication logic change.

For a suspected credential leak, use **Sign out paired devices**, stop internet access, and pair again using fresh links. Restart the host if the private launch credential was exposed. If a trusted session may have executed unwanted commands, investigate the PC itself; session revocation alone does not clean the machine. Report vulnerabilities privately to the repository owner, without publishing live credentials, code, or user workspace contents.
## Native Neovim desktop

Nimlo launches its bundled Neovim through private standard-input/output MessagePack RPC. It does not expose a Neovim RPC socket or grant browsers access to that channel. The engine starts with `-u NONE`, `-i NONE`, and `--noplugin`; its configuration, state, data, and cache directories are private to Nimlo. Installed Neovim plugins and user configuration are not loaded. The pinned upstream archive and its SHA-256 digest are recorded in `neovim-release.json` and checked during the build. Neovim's runtime documentation and license notices are included in the app bundle.

The AppKit editor, file tree, file picker, and search work without a WebView. AI, terminal, sharing, and permission tools use one lazily created WebView in the same window. The tools view authenticates to the app-owned, loopback-only workspace host. Project revisions, authentication, pairing permissions, and provider approval checks also apply to native editing. The host remains the shared authority for document text and history. Neovim does not independently save a competing document history.

Acknowledged drafts are held by the workspace host. Native edits awaiting acknowledgment also have a private pending-copy journal; the app offers recovery rather than silently overwriting a conflicting disk version. The Neovim workspace uses `~/.nimlo-neovim` so it does not automatically adopt other editor recovery directories. Closing the last tools pane releases the tools WebView while keeping the owned shell and AI work alive. Quitting checks pending work and stops the owned host and Neovim processes.

The `--test-control` fixture driver is available only when explicitly requested with an existing, owner-only local directory. It is not a browser endpoint and is not enabled during normal app launches. `make test-native` uses this driver with disposable projects, a real Neovim process, a paired browser, and fake AI providers. Physical input methods, accessibility, and long-running behavior require additional validation.

The current app is ad-hoc signed and not Apple-notarized. Updates are installed manually; there is no configured automatic update feed. Native builds currently support Apple silicon Macs running macOS 13.3 or later. The browser client remains available to paired phones and tablets.
